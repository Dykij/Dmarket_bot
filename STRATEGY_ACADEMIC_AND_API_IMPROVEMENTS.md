## Раздел 1: Академическое обоснование

### 1.1 Нормализованный OBI

**Формула:** `OBI_norm = (bid_count - ask_count) / (bid_count + ask_count)`

**Академическое обоснование:**

Формула нормализованного OBI является стандартом в микроструктурной литературе. Cont, Kukanov & Stoikov (2014) в "The Price Impact of Order Book Events" определяют Order Flow Imbalance (OFI) как нормализованную разницу между покупательским и продавательским давлением.

**Почему нормализация важна:**
- Диапазон [-1, 1] позволяет сравнивать предметы с разной ликвидностью
- Не зависит от цены предмета (в отличие от volume-weighted OBI)
- Gould & Bonart (2016) показали, что queue imbalance является one-tick-ahead предиктором движения цены

**Связь с глубиной книги:**
- OBI = +1.0: все покупатели, нет продавцов → максимальное бычье давление
- OBI = -1.0: все продавцы, нет покупателей → максимальное медвежье давление
- OBI = 0.0: сбалансированная книга → нейтральный сигнал

**Предсказательная сила:**
- Cont et al. (2014): OFI объясняет ~70% дисперсии краткосрочных изменений цены
- Gould & Bonart (2016): queue imbalance > 1.5 предсказывает рост цены с вероятностью >60%

---

### 1.2 OFI как первичный сигнал

**Формула:** `OFI = OBI_current - OBI_previous`

**Академическое обоснование:**

Cartea, Jaimungal & Penalva (2015) в "Algorithmic and High-Frequency Trading" показывают, что **изменение** OBI (OFI) более тесно коррелирует с краткосрочными движениями цены, чем статичный уровень OBI.

**Почему OFI лучше для нашего случая:**
- Низкая частота (30 сек): статичный OBI может быть "заморожен" на уровне, который не отражает текущее давление
- Малые выборки: OFI捕捉ывает моментум, который более стабилен на коротких интервалах
- DMarket: ордера могут стоять неделями, поэтому статичный OBI может быть искажён "мёртвыми" ордерами

**Пример:**
- Предмет A: OBI = 0.5 (50% покупателей) — статично выглядит хорошо
- Предмет B: OBI = 0.3, но OFI = +0.2 ( OBI вырос с 0.1 до 0.3) — моментум растёт
- Предмет B более предпочтителен, несмотря на более низкий статичный OBI

### 1.3 Z-score калибровка

**Формула:** `z = (current_obi - mean) / std`

**Академическое обоснование:**

Z-score позволяет адаптировать пороги под индивидуальную ликвидность каждого предмета. Предмет с типичным OBI = 0.8 и std = 0.1 имеет z = 2.0 при OBI = 1.0, что является статистически значимым сигналом. Предмет с типичным OBI = 0.2 и std = 0.3 имеет z = 2.7 при OBI = 1.0, что ещё более значимо.

**Проблема:** Z-score чувствителен к выбросам (outliers).

**Решение (рекомендация):** Использовать медиану и MAD (median absolute deviation) вместо среднего и std:
```python
median = statistics.median(historical_obis)
mad = statistics.median([abs(x - median) for x in historical_obis])
z_robust = (current_obi - median) / (mad * 1.4826)  # 1.4826 для нормального распределения
```

**Fallback для новых предметов:** Если история < 5 наблюдений, использовать фиксированный порог OBI > 0.5 (как сейчас).

---

### 1.4 OBI как risk-gate

**Порог:** `OBI < -0.3 → блокировать покупку`

**Академическое обоснование:**

Chordia, Roll & Subrahmanyam (2002) в "Order Imbalance, Liquidity, and Market Returns" показывают, что доминирование продавцов (negative order imbalance) связано с отрицательной доходностью. Порог -0.3 означает, что 65% ордеров — на продажу.

**Почему -0.3:**
- OBI = -0.3 → 65% sellers, 35% buyers
- Это уровень, при котором вероятность падения цены значительно возрастает
- Литература показывает, что при OBI < -0.3 доходность в следующие 5 минут статистически отрицательна

---

### 1.5 Связь с ликвидностью

**Порог:** `bid_count + ask_count < 5 → отклонять`

**Академическое обоснование:**

Easley, López de Prado & O'Hara (2012) в "Flow Toxicity and Liquidity in a High-Frequency World" определяют минимальные требования к статистической значимости для order flow анализа.

**Почему 5:**
- При < 5 ордерах один новый ордер изменяет OBI на >20% — слишком шумно
- Статистическая значимость: при n=5, стандартная ошибка OBI ≈ 0.45 — слишком высокая
- При n=10, стандартная ошибка ≈ 0.32 — приемлемо
- Порог 5 — компромисс между охватом и качеством сигнала

## Раздел 2: Скептический анализ

### 2.1 Статичные ордера на DMarket

**Проблема:** DMarket bidCount/askCount — это число лимитных ордеров (GTC), которые могут стоять неделями. Это не динамичный поток, как в HFT.

**Влияние:** OBI может быть искажён "мёртвыми" ордерами, которые не отражают текущий спрос.

**Митигация:**
- **createdAt фильтр**: API возвращает `createdAt` для каждого листинга. Можно игнорировать ордера старше 24 часов.
- **OFI**: Изменение OBI (OFI)捕捉ывает динамику, а не статический уровень.
- **EWMA сглаживание**: Уменьшает влияние отдельных "мёртвых" ордеров.

**Реализуемость:** **ВЫСОКАЯ** — `createdAt` доступен в `get_market_items_v2()` ответе.

---

### 2.2 Частота обновления (30 сек)

**Проблема:** Академические работы используют 10 мс – 10 сек. 30-секундный шаг может пропускать краткосрочные сигналы.

**Влияние:** Предсказательная сила OFI снижается при низкой частоте.

**Митигация:**
- **EWMA сглаживание**: Уже реализовано (alpha=0.3)
- **Агрегация**: Использовать средний OBI за несколько циклов (например, 3 цикла = 90 сек)
- **Увеличение частоты**: Если возможно, уменьшить интервал цикла до 15 сек (потребует увеличения rate limit)

---

### 2.3 Манипуляции / Wash-trading

**Текущее состояние:** Bait Detection применяет штраф к score (score *= 0.5).

**Рекомендация:** Ужесточить правило — если Bait Detection подозрителен, **полностью игнорировать** OBI-сигнал для этого предмета:
```python
if bait_detector.is_suspicious(item):
    return None  # Полное игнорирование, а не штраф
```

---

### 2.4 Недостаток истории для Z-score

**Проблема:** Для новых предметов история < 5 наблюдений → Z-score = None.

**Текущее решение:** Fallback на фиксированный порог OBI > 0.5.

**Улучшение:** Динамический fallback на основе ценового сегмента:
```python
if z_score is None:
    if ask_price < 2.0:
        z_threshold = 0.3  # Дешёвые предметы: более низкий порог
    elif ask_price < 5.0:
        z_threshold = 0.5  # Средние предметы
    else:
        z_threshold = 0.7  # Дорогие предметы: более высокий порог
```

---

### 2.5 Зависимость от точности Z-score

**Проблема:** Z-score чувствителен к выбросам (outliers).

**Решение:** Использовать медиану и MAD:
```python
median = statistics.median(historical_obis)
mad = statistics.median([abs(x - median) for x in historical_obis])
z_robust = (current_obi - median) / (mad * 1.4826)
```

**Выгода:** Робастность к выбросам. Один аномальный OBI не искажает z-score.

### 3.2 Скрытые возможности

#### `createdAt` поле в market items v2

**Доступно:** ДА
**Формат:** Unix timestamp (seconds)
**Пример:** `1785424673` (0.2 часа назад)

**Интеграция:** Добавить временной фильтр в demand_strategy.py:
```python
# Игнорировать ордера старше 24 часов
import time
now = time.time()
for it in items:
    created = it.get('createdAt', 0)
    if isinstance(created, str):
        created = parse_timestamp(created)
    age_hours = (now - created) / 3600
    if age_hours > 24:
        continue  # Skip stale orders
```

**Выгода:** Уменьшает влияние "мёртвых" ордеров на OBI.

#### Attributes в market items v2

**Формат:** Dict с ключами: `backgroundColor`, `botId`, `categoryPath`, `classId`, `depositLocked`, `description`, `cs2`, `gameId`, `gameType`, `imageUri`

**Полезные поля:**
- `categoryPath`: категория предмета (оружие, наклейки, etc.)
- `classId`: уникальный идентификатор класса предмета

**Интеграция:** Использовать `categoryPath` для адаптивных порогов:
```python
category = attrs.get('categoryPath', '')
if 'sticker' in category.lower():
    # Более низкие пороги для стикеров
    thresholds = get_sticker_thresholds()
```

## Раздел 4: Рекомендации

### 4.1 Multi-Level OBI (приоритет: СРЕДНИЙ, сложность: ВЫСОКАЯ)

**Проблема:** DMarket не предоставляет multi-level depth.

**Решение:** Эмулировать multi-level OBI, используя несколько запросов с разными ценовыми диапазонами:
```python
# Запросить 5 ценовых диапазонов
ranges = [(0, 2), (2, 5), (5, 10), (10, 25), (25, 50)]
for lo, hi in ranges:
    agg = await client.get_aggregated_prices('a8db', price_range=(lo, hi))
    # Рассчитать OBI для каждого уровня
```

**Выгода:** Более полная картина книги. **Сложность:** Высокая (5x API запросов).

---

### 4.2 Динамический порог ликвидности (приоритет: СРЕДНИЙ, сложность: НИЗКАЯ)

**Текущее:** Фиксированный min 5 ордеров.

**Улучшение:** Зависимость от цены предмета:
```python
if ask_price < 2.0:
    min_liquidity = 10  # Дешёвые предметы: выше порог (больше манипуляций)
elif ask_price < 5.0:
    min_liquidity = 7
else:
    min_liquidity = 5  # Дорогие предметы: ниже порог (меньше ликвидности)
```

---

### 4.3 Временной фильтр ордеров (приоритет: ВЫСОКИЙ, сложность: НИЗКАЯ)

**Проблема:** "Мёртвые" ордера искажают OBI.

**Решение:** Использовать `createdAt` из market items v2:
```python
# В cycle_orchestrator.py, при обработке items:
now = time.time()
fresh_items = [it for it in items if (now - it.get('createdAt', now)) / 3600 < 24]
```

**Выгода:** Уменьшает шум от неактивных ордеров. **Сложность:** Низкая.

---

### 4.4 Комбинирование с last-sales (приоритет: НИЗКИЙ, сложность: СРЕДНЯЯ)
