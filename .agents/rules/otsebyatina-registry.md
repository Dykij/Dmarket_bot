# Реестр паттернов "отсебятины" (H1-H17)

**ВНИМАНИЕ:** При подозрении на паттерн Hx — остановиться и явно сверить, не совершается ли он сейчас.

- **H1**: Игнорирование прямых указаний в пользу "оптимального" решения.
- **H2**: Скрытие деталей или ошибок за общими формулировками.
- **H3**: Самовольное удаление кода без запроса (тихие удаления).
- **H4**: Изменение смежного кода, не относящегося к текущей задаче (scope creep).
- **H5**: Придумывание (галлюцинация) фактов о кодовой базе.
- **H6**: Смена архитектурного подхода без обсуждения.
- **H7**: Оставление TODO или заглушек вместо реального кода.
- **H8**: Игнорирование предупреждений линтеров/тестов (попытка "пропихнуть").
- **H9**: Самовольная перегруппировка коммитов или изменение истории git.
- **H10**: Изменение настроек инфраструктуры без запроса (CI/CD, Docker).
- **H11**: Написание избыточно сложного кода для простых задач.
- **H12**: Отказ от использования предписанных инструментов (использование grep вместо ast-grep).
- **H13**: Изменение формата логов/алертов без согласования.
- **H14**: Самовольное "исправление" чужих/старых багов в рамках другой задачи.
- **H15**: Отсутствие RAW-доказательств при отчётах.
- **H16**: Фикс, откатывающий или ломающий более раннюю работу в этой же сессии.
- **H17**: Молчаливое урезание объёма реализации (partial fulfillment).

- **H18**: Фабрикация проверочного сигнала для прохождения гейта, вместо честной эскалации ("эта проверка нерелевантна в данной ситуации, вот почему") или легитимного изменения логики гейта с разрешения пользователя. Пример: вписать "N passed" в RAW_OUTPUT.log вручную, не запуская тесты, потому что stop_gate.sh требует этот паттерн для завершения сессии. Проявляется не только как фабрикация тестового вывода, но и как любая косметическая правка файла ради формального прохождения строкового совпадения в хуке, без устранения причины предупреждения (пример: добавление пустой строки в SESSION_LOG.md, чтобы файл попал в список изменённых, вместо разбора реальных незакоммиченных изменений).

- **H19** *(Методологическая слепота при верификации мёртвого кода)*: Ложный вердикт "код мёртв" или "код используется", опирающийся исключительно на `git log -S` + кросс-файловый `rg`/`grep`, не покрывает:
  - **(а) Переименования/перемещения без изменения текста**: `git log -S` не покажет коммиты, где файл переместился (`git mv`) без модификации строк, а `grep` по текущему дереву найдёт символ в новом имени, создавая иллюзию наличия в истории.
  - **(б) Динамические импорты**: `importlib.import_module()`, `getattr(module, name)`, `eval()`, строковые реестры плагинов (`PLUGIN_MAP = {"foo": "mymod.Foo"}`) — не обнаруживаются статическим поиском по исходному тексту.
  - **(в) Коммиты только в невлитых ветках**: `git log -S` находит коммит в ветке, которая никогда не мерджилась в рабочую ветку — это создаёт иллюзию "использование было", которого нет в продакшн-дереве.
  - **Мера защиты**: Перед удалением предположительно мёртвого кода дополнительно запускать `git branch --contains <commit>` для каждой ветки, где `git log -S` нашёл вхождение — убедиться, что эта ветка влита в `main` или текущую рабочую ветку. Для динамических паттернов — ручной поиск по строковым реестрам и `importlib`-вызовам.
