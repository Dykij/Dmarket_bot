# Documentation Grounding (обязательная сверка с источником)

## DMarket API — любое поведенческое решение в коде
Первичный источник для проверки эндпоинтов и схем: https://docs.dmarket.com/v1/swagger.html (официальный Redoc, Trading API v2.0.0). Обращаться через WebFetch, не через curl из шелла — сетевой allowlist рабочей директории блокирует прямой доступ к этому домену.

ВНИМАНИЕ: обнаружено расхождение между независимыми фетчами этого URL (2026-09-25) — один и тот же адрес может отдавать структурно разный контент в зависимости от вызывающего инструмента/сигнатуры запроса, возможно из-за Cloudflare anti-bot защиты. Перед тем как доверять содержимому — сверить характерные маркеры реального документа: заголовок "DMarket trading API (v2.0.0)" (НЕ просто "DMarket API"), рендерер Redoc v2.5.4, разделы "Buy items"/"Sell Items" (НЕ "Trading"/"Market"/"Exchange"). Если полученный контент не содержит этих маркеров — считать результат ненадёжным и не использовать для поведенческих решений в коде. Если маркеры не совпадают — не сразу помечать как NOT_VERIFIED: повторить WebFetch/read_url_content ещё один раз немедленно (Cloudflare-челлендж часто разовый, не постоянный — сегодня 2026-09-25 повторный вызов сразу дал настоящий документ). Только если маркеры не совпадают и после повторной попытки — тогда NOT_VERIFIED и эскалация пользователю.

Перед написанием или изменением кода, который:
- обращается к новому или ранее не задокументированным явно эндпоинтам DMarket API,
- интерпретирует статусы предметов/офферов (`trade_protected`, `reverted`, `active`, `sold` и т.п.),
- закладывает предположение о комиссиях, лимитах запросов (rate limits), задержках вывода средств, поведении Trade Protection,
- мигрирует с одной версии API на другую,

— агент обязан:
1. Свериться с официальным источником: `support.dmarket.com` (Help Center), `dmarket.com/blog` (раздел Product-Updates/API), или официальной Trading API документацией в настройках аккаунта DMarket.
2. Процитировать дословно (не пересказом) релевантный фрагмент источника, с URL и — если есть — датой публикации/обновления статьи.
3. Явно указать в комментарии к коду или в коммит-сообщении, на какой источник опирается конкретное поведенческое решение (например: `# Per support.dmarket.com/hc/.../43414412402961, updated 2026-02-11: items with no Trade Protection withdraw immediately`).
4. Если официальный источник не даёт прямого ответа — явно зафиксировать `NOT_VERIFIED: источник не найден`, не полагаться на память о более раннем прочтении документации без даты/цитаты.
5. При наличии нескольких источников с разными датами — приоритет у более свежего (сверять дату "Updated" на странице Help Center, а не полагаться на порядок в поисковой выдаче).

**Не полагаться на:**
- Внутреннюю память о том, "как это работало раньше" без даты подтверждения.
- Комментарии в коде без даты и ссылки на источник, если они старше 2-3 месяцев — DMarket API меняется (миграции v1→v2, новые статусы полей уже подтверждённо происходили в 2026 году).

## Python — стилистические и идиоматические решения

Перед нетривиальным стилистическим или архитектурным решением в Python-коде (не для тривиальных вещей вроде именования переменных) — сверяться с официальной документацией:
- `docs.python.org` — для поведения стандартной библиотеки, типизации (PEP 484/526), синтаксиса.
- PEP 8 — для форматирования и стиля.
- PEP 257 — для докстрингов.

Не гадать о поведении стандартной библиотеки или сторонних пакетов (`asyncio`, `sqlite3`, `pydantic`) по памяти, если поведение критично для корректности (например, thread-safety, ordering гарантии, деприкейшены между минорными версиями) — проверять напрямую через `context7` или официальную документацию перед тем, как утверждать, что "так и должно работать".

**Не заменяет** существующие правила: `libcst`-only для структурных Python-правок, `ast-grep`/`tgrep` вместо `grep` для структурного поиска, `difftastic` для семантической проверки диффов — эти правила остаются в силе, документационная сверка — дополнительный, не замещающий слой.
