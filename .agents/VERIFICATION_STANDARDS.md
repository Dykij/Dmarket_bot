# Стандарты верификации — обязательны для каждой задачи, меняющей код/конфиг

Каждый пункт ниже возник из реального инцидента в этом проекте, не абстрактного пожелания.

## 1. Многофайловые изменения — показывать результат по КАЖДОМУ файлу

Если правка касается N файлов — в конце должен быть `cat`/`git diff` для всех N,
не для одного "представительного". 
*Инцидент: heartbeat-строка была реально удалена из `pre_bypass_gate.sh`, но тест
показывал только этот файл, создавая ложное впечатление, что `stop_gate.sh`
(где проблема оставалась) тоже исправлен.*

## 2. RAW — вставленный текст, не пересказ и не "сохранено в файл"

Если промт просит "покажи RAW" — в чат идёт весь вывод команды целиком.
Фразы вида "полный вывод сохранён в файл, вот выдержка" не считаются выполнением.
*Инцидент: несколько раз усечённый вывод grep выдавался за "полный RAW".*

## 3. Явно называть границы того, что доказано

Если тест подтверждает только часть заявленного — сказать прямо, что именно
осталось непроверенным, а не позволять читателю обобщить самому.
*Инцидент: тест `pre_bypass_gate.sh` (deny/allow) был представлен как подтверждение
работы над `stop_gate.sh`, хотя не имел к нему отношения.*

## 4. `git diff` — непосредственно ПЕРЕД коммитом, не после

Перед каждым `git commit` — показать `git diff` того, что сейчас коммитится.
Если diff пустой — остановиться и разобраться, не коммитить пустое.
*Инцидент: `git commit --amend` "исправления" `stop_gate.sh` в реальности
закоммитил 0 изменений в этот файл — узнали только через археологию `git log`
постфактум.*

## 5. `git branch` не сохраняет незакоммиченные изменения

Метод temp-branch (`git branch X && git checkout HEAD -- file && ... && git checkout X -- file`)
для регрессионной изоляции работает ТОЛЬКО если фикс уже закоммичен на момент
создания ветки. Для незакоммиченного изменения — сначала закоммитить (even as WIP),
либо использовать `git stash` явно и осознанно для одного этого шага.
*Инцидент: `ranking.py` фикс был незакоммичен, `git branch` не подхватил его,
"восстановление" в конце вернуло старую версию — заметили и вручную исправили,
но само использование метода было ошибочным для этого случая.*

## 6. Новая находка, противоречащая ранее зафиксированной — явная сверка, не молчаливая замена

Если новый результат расходится с уже установленным фактом — сказать прямо
"это расходится с тем, что мы установили раньше, вот почему", не просто
подставить новый вывод вместо старого.
*Инцидент: сравнение `ENDPOINT_LIMITS` бота с неавторизованными лимитами DMarket
(2 RPS) вместо авторизованных (110 RPS) едва не привело к ложному выводу
"критичное превышение лимита в 27 раз", хотя конфиг был корректен.*

## 7. Никакого временного/отладочного кода в постоянных файлах

Heartbeat-логирование, временные print/echo для диагностики — удаляются
до коммита. Если что-то добавлено "только для теста" — явный отдельный шаг
"убрать" обязателен перед тем, как считать задачу завершённой.
*Инцидент: heartbeat-строки едва не остались в хуках навсегда.*

## 8. Ничего не удалять без показа списка на подтверждение

Правило действует всегда, не только для явно помеченных задач.
*Инцидент: удаление `scripts/qartez-bridge/` и `docs/tradebotcs2_demo_analysis.md`
под видом "старого мусора" без показа списка — оба оказались ценными.*

## 9. Не коммитить перестраиваемые кэши/индексы

Директории вроде `.qartez/` (индекс, автоматически перестраивается) — в `.gitignore`,
не в git.
*Инцидент: `.qartez/` была закоммичена вместе с другими изменениями.*

## 10. Блайнд-regex по коду — только через ast-grep/libcst, не голый `sed`/`re.sub`

Правки Python-кода через самодельный regex-скрипт создают риск синтаксической
порчи (экранирование, кавычки), требующий повторного патча.
*Инцидент: патч `ranking.py` через `re.sub` внёс лишние обратные слэши
(`f\"`), потребовавшие второго корректирующего прохода.*

## Применение

Каждый промт, меняющий код/конфиг/хуки, должен явно ссылаться:
"Следуй `.agents/VERIFICATION_STANDARDS.md`" — вместо повторного перечисления
всех этих пунктов заново.
